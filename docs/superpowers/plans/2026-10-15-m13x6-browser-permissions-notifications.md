**Goal:** a person browsing in a Browser profile is asked "Allow Notifications", "Allow Location", "Allow Camera", "Allow Microphone" or "Allow Camera and Microphone" with iTerm2's texts the first time a site asks, the answer is remembered per origin in the browser database and honored from then on, a site's notifications appear as Tandem notifications, audio is muted until the person allows the origin through iTerm2's four-button question bar, the toolbar menu lists the current site's saved permissions to reset and offers "Unmute Current Page", `iterm2-about:permissions` lists, filters and revokes every saved permission (reloading the pages that used it), and the session indicators show in the toolbar.

**Architecture:** pure models first, each a plain `pub mod` tested on EXTREME without a web view. `browser_perms.rs` (pure) is iTerm2's permission vocabulary: the six types with raw values and texts, the two decisions, origin normalizing, the mapping from WebView2's permission kinds, the system-state rules for Windows notifications and location, request grouping, the per-site menu items, the permissions page's paging and filters and its reply scripts, and the audio state machine. `browser_db_perms.rs` holds the `BrowserPermissions` table verbatim and its queries as an `impl crate::browser_db::Db` block (13x2's `EXTRA_SCHEMAS` and `conn()`). `browser_indicators.rs` (pure) is the toolbar's indicator strip: iTerm2's order, help texts, glyphs and the width rule. The host (13x's `webhost.rs`/`webhost_win.rs`) gains the WebView2 events and calls iTerm2 had to build polyfills for: `PermissionRequested` with a deferral, `NotificationReceived`, the document-playing-audio state, `IsMuted`, and the profile's per-origin permission state (Decision: native WebView2, no polyfill scripts). The app side is `src/app/browser_perms_app.rs` (requests, the dialog through 13b's alert path, mirroring decisions into the WebView2 profile, revocation reloads, notifications, audio, the menu items, the page's messages) and the indicator strip drawn by 13x Task 6's toolbar painter in `src/app/browser_app.rs`. The per-pane state lives in 13x's `BrowserView` (app-wide `browser_views`, keyed by pane, so no `swap_live` entry).

**Tech Stack:** as 13x and 13x2. No new crate. `webview2-com` 0.39.1 (13x) gives `ICoreWebView2PermissionRequestedEventArgs3` (`SavesInProfile`), `ICoreWebView2_8` (`IsMuted`, `IsDocumentPlayingAudio`, `IsDocumentPlayingAudioChanged`), `ICoreWebView2_13` (`Profile`), `ICoreWebView2Profile4` (`SetPermissionState`, `GetNonDefaultPermissionSettings`) and `ICoreWebView2_24` (`NotificationReceived`, `ICoreWebView2Notification`). `rusqlite` (12c) through 13x's `browser_db`. `serde_json`. `windows-sys` gains `Win32_System_Registry` (approved in the 13g rulings; skip if 13g already added it) for the two Windows privacy switches.

### Decisions (each goes in `m13x6-rulings.txt`)

- Native WebView2 permission, notification and mute support instead of porting `Polyfills/` and `AudioMuting/` scripts. Cost: geolocation error texts and the `Notification` object's fine behavior are Chromium's, not iTerm2's polyfill's; the whole page mutes instead of the frames that played.
- Tandem's database decides. A saved notification or location answer sets `SavesInProfile` true so WebView2 holds it before the page's promise resolves (a `SetPermissionState` beside the deferral would race it); every other answer sets it false; revocation and reset go through `SetPermissionState`; the start-up sync rewrites kinds 1 to 4 from the database and never touches other kinds. Cost: one sync per start; a mirror failure is logged and the next request re-asks.
- Camera and microphone decisions are never mirrored into the profile: each media request is answered from the database by exact type, as iTerm2 (`BPM:27`). Cost: none known; WebView2 raises a request per `getUserMedia` call and Tandem answers it without a dialog.
- Requests this plan does not decide (kinds `from_kind` rejects; tool, popover and Quick Look views) are completed untouched, so WebView2's own prompt shows and remembers its answer. Cost: WebView2's prompt differs from iTerm2's (iTerm2 has no such kinds).
- Opaque and host-less requesters (`data:`, `about:`, `javascript:`, `file:`, a URL with no authority or a malformed scheme) are denied without a dialog and without saving; `blob:` URLs use their inner origin; IPv6 hosts keep their brackets. Cost: a local HTML file cannot get notifications or location (iTerm2 would ask once for all `file://` pages together).
- Camera and microphone requests of one origin drained in one tick become one CameraAndMicrophone question. Cost: requests split across ticks ask twice (each saved separately).
- A closed permission alert window, or one that never shows, blocks the request without saving (R13x67-1): 13b's alert path gains an explicit close result (`scripts_alerts::Answer::Closed`) routed only for `Then::BrowserPermission`, because its default close answer presses Cancel or else the first button, which here is Allow. Cost: none known (iTerm2's modal alert cannot be closed without a button).
- Permission kinds iTerm2 never asks about (clipboard read, sensors, downloads, file access, autoplay, fonts, MIDI, window management) keep WebView2's default handling: their requests are completed untouched (WebView2 remembers its own answer) and the start-up sync never resets them. Cost: WebView2's own prompt appears for them.
- Requests from tool, popover and Quick Look views are completed untouched (WebView2's default). Cost: none; iTerm2's factory views have no permission manager.
- Windows privacy switches are read from the registry (notifications `ToastEnabled`, location `ConsentStore`) and never prompted. Cost: a policy-managed machine that sets them elsewhere is read as allowed.
- Pre-muting at the start of each new document when the origin is not allowed, and unmuting there when it is (a redirect re-evaluates on its target without resetting the once answers); a play event from a granted origin while muted unmutes. Cost: none audible; iTerm2 could let the first moment of sound through before muting.
- Allow Always saves the row wherever the pane has navigated since (as iTerm2) but unmutes only when the pane still shows the origin asked about, because Tandem mutes the whole view. Cost: none known.
- Every play event from an undecided origin asks again, as iTerm2; 13x2's `browser_announce` keeps one bar per identifier and answers a duplicate as closed. Cost: none.
- A web notification without a body shows its origin as the body (an empty tray balloon body removes the balloon). Cost: a line of text iTerm2 does not show.
- Web notifications use Tandem's one tray balloon; a click reveals the browser pane; the page's close clears the balloon only when it is the one on screen. Cost: no stacking of several web notifications.
- The permissions page's reply scripts quote arguments as JSON strings (iTerm2 escapes only `'`). Cost: none.
- An offset past the end of the permission list answers an empty page. Cost: none (iTerm2 would crash).
- The site menu items are spliced before Settings instead of changing `browser::menu_items`' signature; they carry no icons. Cost: a second builder to keep in iTerm2's order.
- The indicator help popover is 360 by 80 points showing the help's text with links reduced to labels. Cost: iTerm2's clickable help links (Unlink from AI Chat, Reveal AI Chat, Stop sending) are not clickable.
- The toolbar's indicators are every one iTerm2 feeds a browser session that Tandem can compute (Maximized, the broadcast pair, Alert, CopyMode, DebugLogging, Pinned, the AI pair, ShowRememberedAlerts), fed here from their owners' state; Coprocess, AllOutputSuppressed, ZoomedIn, Filter, Secure Keyboard Entry (macOS only), Channel, BufferingInput and ScreenshotMode never apply to a browser pane. Too many indicators are clipped, not scrolled. Cost: no horizontal scrolling of an overflowing strip.
- Copied iTerm2 files stay in `resources/browser/` with their headers and iTerm2's GPL-2.0 license text beside them (ruling Q5 as amended, PROVISIONAL pending Robert). Cost if wrong: rewriting the two permissions page files before a public release.

### Pitfalls for the implementer

- Take `GetDeferral` in `PermissionRequested` and return at once; the alert may stay open for minutes. A view closed with a pending request completes it with Default, or WebView2 leaks the request.
- `SetPermissionState` and `GetNonDefaultPermissionSettings` are asynchronous; never wait on them inside a winit callback. Clear then set in the completion chain, in order.
- `SavesInProfile` must be set before `State` and before completing the deferral; an `Untouched` answer sets neither.
- `IsDocumentPlayingAudio` stays true while muted; do not treat "playing" as "audible". `IsDocumentPlayingAudioChanged` fires on each change; each change to true is one iTerm2 play event (13x2's duplicate-id rule stops a second bar).
- `NotificationReceived` needs `ICoreWebView2_24`; when the runtime is older, WebView2 shows its own toast. Log once and let it.
- The announcement bar is 13x2's `browser_announce`; its `place_browser_views` already keeps the web view below the front bar. Do not add a second bounds rule.
- A permission alert must never be answered by 13b's default close index: route `CloseRequested` and a dropped ask for `Then::BrowserPermission` to `scripts_closed`, or closing presses Allow.
- Dev Null panes use the InPrivate `BrowserDevNull` environment and the in-memory database; never mirror their decisions into the `Browser` profile.
- Origins in the registry keys and URLs are data: bound SQL parameters, JSON-quoted scripts, never string-built SQL or JS.
