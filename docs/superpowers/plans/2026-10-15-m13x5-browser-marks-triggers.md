**Goal:** in a browser pane a person can name a spot on a page (from the Edit menu, the page's context menu or the Named Marks tool), see it annotated on the page with a rename and delete box, find it again from Edit > Named Marks, the Named Marks tool or Open Quickly even after closing the page, and give a Browser profile triggers that highlight or link text on pages, inject JavaScript, reload a page after a delay, enter reader mode or enter and leave a workgroup, exactly as iTerm2 does.

**Architecture:** pure models first, each a plain `pub mod` tested on EXTREME without a web view. `browser_marks.rs` (pure) is iTerm2's `Location`, the `iterm-mark:` fragment, the add rules, the page messages, the annotation data, the reveal decision, the app-wide mark cache and the filled JavaScript templates. `browser_marks_db.rs` holds the `BrowserNamedMarks` table and its queries as `impl crate::browser_db::Db` blocks over 13x2's `Db::conn()`. `browser_triggers.rs` (pure) is the trigger JSON sent to a page, the `setTriggers` call, the match event parser, parameter resolution and the action-to-effect table. `triggers.rs` gains the browser catalog next to the terminal one, and `settings_triggers.rs` gains the browser-mode editor. The app side is `src/app/browser_marks_app.rs` (the add prompt, adding, annotations, the two page message handlers, reveal, rename, remove, the terminal UI hooks) and `src/app/browser_triggers_app.rs` (the trigger script, its messages, the effects, resending on a profile change). Every new App field is app-wide and keyed by `PaneId` (as 13x's `browser_views`), so none goes in `swap_live`. All page JavaScript is iTerm2's, copied unchanged into `resources/browser/`, read through 13x2's `browser_js::resource` table and filled by `browser_js::fill_template`. Every script iTerm2 evaluates in `.defaultClient` (all the Marks scripts and the trigger engine, highlight and hyperlink calls) runs in Tandem's isolated world: the trigger engine as a document-start Client `UserScript` from `browser_user_scripts`, the rest through 13x2's isolated-world script runner `App::browser_js_call`; only the two Inject Javascript actions and Reload After Delay run in the page world, through 13x2's page-world runner with no bridge and no secret (R13x23-1, R13x45-1).

**Tech Stack:** as 13x and 13x2. No new crate: `rusqlite` (12c) through 13x2's `Db::conn()`, `serde_json`, `uuid` (mark guids, trigger identifiers), `regex` (none new; the trigger regexes run in the page as JavaScript `RegExp`, as iTerm2's do), `muda`, `egui`. One addition to 13x's host: `Event::DocumentMethod` and `ViewSetup.track_document_method` (Task 3). No other WebView2 call: scripts go through 13x2's runners.

### Corrections to the research (the source wins)

- A browser session's named marks are every mark of the browser user, not the page's; the list is newest first, not current-page first (`NMM:552-558` versus the comments at `BVC:571-575`, `AD:4310-4311`, `TNM:130`).
- Edit > Mark (Save Scroll Position) in a browser session opens the Add Named Mark dialog (`PS:16755-16771`).
- iTerm2 pastes XPath and text fragment values into JavaScript string literals unescaped (`NMM:445-457`, `NAV:8-12`); a page-controlled attribute in the XPath can break or inject script (fixed, Decision).
- Highlight Text browser triggers with P3 colors draw nothing in iTerm2 (`HGT:120-130` passes "p3#..." to CSS).
- `iTermBrowserNamedMark` rows with a URL lacking a location are listed in menus but never annotated (`NM:74-80`).

### Decisions (each goes in `m13x5-rulings.txt`)

- Every Marks script and the trigger engine, highlight and hyperlink calls run in Tandem's isolated world (R13x23-1, R13x45-1: iTerm2's `.defaultClient`): the trigger engine as a document-start Client user script, the rest through 13x2's isolated-world runner, whose answers come back from `Runtime.evaluate` and whose posts reach Tandem only through the binding; the view secret appears in no 13x5 script, and the marks and trigger secrets only in isolated-world scripts. Inject Javascript and Reload After Delay run in the page world with no bridge and no secret (`BTH:134-138`). Cost: none visible; if 13x2's probe failed, named marks on pages and browser triggers are inert and recorded partial rather than moved into the page world.
- Values substituted into JavaScript string literals are escaped (`js_literal_inner`, built on 13x2's `js_string`), `{{SECRET}}` is substituted before person- or page-supplied values. Cost: none visible; a deviation from iTerm2's raw paste (R3 security fix).
- Mark URLs are encoded as `URLComponents.fragment` encodes them (the text fragment twice) and decoded with Foundation's strict `removingPercentEncoding` rules (review I1). Cost: none; stored URLs match iTerm2's.
- The main-frame HTTP method comes from a Document-context `WebResourceRequested` filter (`Event::DocumentMethod`, decided by `document_method_applies`); a navigation with no request seen (a back-forward cache restore) counts as GET. Cost: a POST result restored from the cache allows a mark whose reveal reloads the URL with GET.
- The add gate follows iTerm2 per path: the Edit menu refuses non-http(s) and non-GET pages before the prompt; the context menu and the Named Marks tool open the prompt and refuse only a known non-GET method after OK (review M11). Cost: none (iTerm2 behaves the same).
- A refused Edit > Set Named Mark does nothing instead of being greyed out (Tandem's menu items are enabled once). Cost: no visual cue on POST pages.
- The mark prompt is queued and opened from `about_to_wait`, sharing the terminal's Set Named Mark prompt slot (review I2, M9). Cost: a browser and a terminal Set Named Mark window are never open at once (a second request focuses the first).
- The mark cache is app-wide per store (normal and Dev Null), not per browser session. Cost: none (iTerm2's caches all read the same database).
- Browser trigger class names: iTerm2's module-qualified names are written; the bare Swift names are read as synonyms (writer questions 1-48, accepted as stated). Cost: if iTerm2's module name differs, imported Reader Mode, Highlight and Hyperlink triggers are read through the synonyms only.
- Highlight colors: "#rrggbb" kept, "p3#..." converted to `color(display-p3 ...)`; the editor writes sRGB "#rrggbb" and drops the clear text alpha iTerm2 stores for new triggers. Cost: a deviation where iTerm2 draws nothing.
- Highlight and Enter Workgroup skip parameter resolution (iTerm2 discards Highlight's resolved text, `HGT:120-130`, and uses Enter Workgroup's id as stored, `EWB:106`; review M10). Cost: an interpolation error in a Highlight parameter is not reported, where iTerm2's resolution might report one.
- The "+" default browser trigger is written with `matchType` 0, the value iTerm2 reads for its absent key (`TC:481-490`; review M6); `addTrigger:` starts at URL Regex as iTerm2's panel does. Cost: the "+" default fires nothing until its action is picked again, as in iTerm2.
- Browser regexes are not compile-checked in the editor (they are JavaScript `RegExp`, checked in the page). Cost: a bad pattern is noticed only in the page log.
- The trigger script is added to every browser view. Cost: one message per page load for profiles without browser triggers.
- The two workgroup actions and Enter Reader Mode stay "not available yet" until 13y1 and 13x4 are built. Cost: those actions do nothing before then.
- A pane's trigger list is reloaded and resent only when its browser-action triggers' stored tables change (review I3, iTerm2's `observeDictionary(key: KEY_TRIGGERS)`); the reload keeps the secret. Cost: none.

### Pitfalls for the implementer

- 13x2's bridge rewrite (its `wrap` for the trigger user script, its runner for on-demand bodies) must cover `window.webkit?.messageHandlers?.iTerm2Trigger` captured into a variable and called later (`TJS:20`) as well as the plain form (`LCM:22`, `SHOW:212`, `:240`); the ignored runtime tests of Tasks 4 and 9 catch a miss. If it does not, fix it in 13x2 (one path), never by editing the copied file.
- `NavigationCompleted` does not fire for same-document fragment navigations; a same-page reveal must not wait for `Navigated` (Task 5 runs it at once).
- `window.iTerm2Triggers`, `window.iTermLayoutChangeMonitor` and the annotation handlers live only in the isolated world: every call that touches them (highlight, hyperlink, `setTriggers`, the monitor toggles, the position update) must go through the isolated-world runner, never the page-world runner or a plain `execute_script`, or it silently finds nothing. The isolated world is recreated for each document, so the monitor is started again after every successful navigation (Task 4 already does).
- `update-mark-positions.js` and `navigate-to-named-mark.js` are expressions ending in `})();`; prefix `return ` for the runner, never wrap them in another function.
- No 13x5 script may contain the view secret; `marks_scripts_use_the_isolated_world` and `trigger_scripts_use_the_right_world` guard it.
- Dev Null panes use the in-memory database; never write their marks to disk and never mix their cache with the normal store's.
- The runners answer asynchronously; a pane closed before the answer drops its callbacks (13x2's pending calls go with the view); the chained `marks_modify_dom` closures and a queued mark prompt must tolerate a missing pane.
- The Hyperlink default parameter is typed with a backslash: keep `"https://\\0"` in Rust source.
