**Goal:** a person with AI enabled can press Win+Y at a shell prompt, describe a command in plain English and get it in the large Composer; press Win+Alt+Y after a command and get an AI chat whose bullets link to yellow-underlined annotations in the terminal; see AI completions and replacements while typing in the Composer when AI Completion is on; and run Codecierge in the toolbelt, which watches each finished command and suggests (or, when allowed, runs) the next step, exactly as iTerm2 does, with nothing sent before the gate and each feature's own consent.

**Architecture:** pure models first, each a plain `pub mod` tested on EXTREME. `ai_engage.rs` holds Engage AI's input rules, texts, the skip key and the Composer result rules; `ai_engage_ui.rs` its two egui windows (the dialog and the wait window). `ai_explain.rs` holds the explanation request, response, update and annotation types with iTerm2's Codable JSON, the prompt, the streaming parser, the chat bullets, and Explain's selection, cap, title, subject, located-text and annotation-placement rules. `ai_complete.rs` holds the Composer AI prompt, line parser, `{{FILE}}` expansion and the merge with file and history items. `codecierge.rs` holds Codecierge's per-session model, texts, prompts, feed messages, functions and the Windows write plan. The app side is `src/app/ai_runs.rs` (12e's table of 12b `Runner`s: start with the vendor key, the key prompt, polling, routing each finished answer to its owner), `src/app/ai_engage_app.rs` (Engage from the terminal and both Composers, the wait window, results), `src/app/ai_explain_app.rs` (the menu item, the chat hand-off, the App-level explanation processor, hidden annotations, reveal) and `src/app/codecierge_app.rs` (the conversation, `execute`, `write`, the command-exit feed); Codecierge's views are drawn in the toolbelt by `src/app/toolbelt_more_ui.rs` and `src/scene.rs` as today. Every new App field is app-wide (Codecierge sessions are keyed by session guid, as iTerm2's registry); none goes in `swap_live`.

No new crates: 12b's WinHTTP transport through `windows-sys` (ruling 4), `regex` (the `{{NAME}}` and annotation patterns), `serde_json` (function arguments, the explanation JSON), `uuid` (annotation ids), `pulldown-cmark` through `porthole::render` (Codecierge's transcript), `egui` through `EguiHost` (the Engage windows).

### Decisions (each goes in `m12e-rulings.txt`)

- The `shell` session variable is the shell integration's shell, else locally the profile program's file name without ".exe" (iTerm2 keeps the last path component, which on Windows would carry ".exe"); `uname` is "Windows_NT" locally and unset for a remote host (iTerm2 has it only through its SSH conductor, which Tandem does not have). Cost: a remote prompt reads "on " with an empty `uname`, as iTerm2's without the conductor.
- This plan's alerts use 12a's AI alert queue (`App::ask_ai`, ruling 12c-7), adding `Then` variants; the one-vendor key prompt is 12a's `App::ask_ai_key` (ruling 12e-1), to which this plan adds `KeyThen` variants. Cost: none.
- An Engage prompt template that fails to evaluate sends nothing and shows nothing, as iTerm2's nil result. Cost: a broken custom template looks like a dead key.
- The Engage dialog and the wait window are egui windows (Windows has no sheet); the dialog's field is multi-line, Shift+Enter sends, Enter inserts a newline. Cost: a separate window where iTerm2 slides a sheet.
- The long-text reason drops iTerm2's warning emoji and draws the Segoe Fluent Icons warning glyph before "The selected text was rather long."; the wait window draws no `aiterm` image. Cost: a different look.
- Engage cuts a long query in UTF-16 units as iTerm2 but never splits a surrogate pair. Cost: up to one unit shorter.
- The terminal path puts the model's text in the Composer as given (iTerm2 trims backticks only in the Composer path). Cost: as iTerm2.
- Tandem has no selected-command mark, so Explain uses the selection or the last command mark. Cost: no explaining of an older command without selecting it.
- The selection link in an explanation request is Tandem's `iterm2:/compound-location?session=<guid>&sub=<x0>,<y0>,<x1>,<y1>` in absolute lines (iTerm2 encodes line-buffer positions); annotation links keep iTerm2's `iterm2:annotation?ann=<id>&s=<guid>`; both are routed in-app (12d) and never handed to the OS. Cost: an imported iTerm2 chat's selection links do not resolve.
- The explanation parser takes the `<response>` text between its tags before cutting them out (iTerm2 indexes the edited string with positions from before the cut, `XRM:100-112`, which reads the wrong span; ruling 12e-3, recorded as a fixed iTerm2 bug). Cost: a response that iTerm2 would garble reads correctly.
- Explanation messages keep iTerm2's Swift JSON (keys, optional keys absent, `gridCoords` as `{"coords": [{"x", "y"}]}`) so an imported `chatdb.sqlite` explanation opens and re-saves unchanged; annotation ids are fresh UUID strings as iTerm2's `PTYAnnotation.uniqueID`. Cost: none.
- The explanation processor runs as an App-level call at the top of 12c's `App::chat_publish` (iTerm2's client processor needs the terminal sessions, which 12c's broker processors cannot reach). Cost: one call in 12c's publish path.
- Revealing an annotation scrolls to it and opens it as Next Annotation does (Tandem has no note highlight flash). Cost: a window instead of a flash.
- The Composer cancels a pane's in-flight AI request when a newer fetch starts (iTerm2 lets it run and drops the answer by generation; ruling 12e-5, a recorded deviation). Cost: none visible; fewer paid calls.

### Pitfalls for the implementer

- A provider key or a prompt is never logged: no `Debug` print of a `Request`, no banner with the prompt, no test output containing either.
- Never make a network call in a test: every AI result in a test comes from 12b's fake transport or from a pure function.
- The wait window's Cancel must remove the pending id; a `Done` for a removed id does nothing (a late answer must not overwrite the Composer).
- Composer AI replies race the typing: check the generation before touching `ghost` or `popup`, and never let a replacement become ghost text (it would append a whole command after the user's text).
- UTF-16 everywhere offsets come from the model (annotation offsets, Engage's length rule); Rust strings index bytes.
- Annotation placement uses the request's `base_offset` plus the stored grid line, converted with `grid_line` against the facts now; output can scroll between request and answer.
- `add_note` refuses the alternate screen and lines outside the grid (it returns 0): no bullet for those.
- Codecierge's `pending` call must be answered exactly once; a pane closing answers it with `SESSION_GONE` and drops the session.
- The usage warning is permanently silenceable: a remembered Stop must still end the task each time it is due.
- Every new App field is app-wide; none goes in `WinSlot` or `swap_live`.
- Never call `Runner::start` outside `ai_runs::launch`; a stored key is not permission (ruling R12e-1).
- Never build a direct-write path with `Path::join` on the model's filename alone: `join` replaces the base for `\x`, `C:x` and absolute names. Go through `direct_path` then `write_direct` (ruling R12e-2).
- Never type the AI's text through `paste_text`; use `user_write(.., Write::Agent)` (ruling R12e-4).
- 12c's `chat_agent::user_text` gains the `mode` argument in Task 3 (minor M7): update its callers in the same commit, which are 12c's history rebuild (`history`, the `MessageToPromptStateMachine` walk), the turn's `Body::Text(user_text(c))` built at the turn's start in 12c's `Engine` (`src/app/chat_app.rs`), 12c's test `user_text_follows_iterm2`, and 12f Task 11's `WatcherEvent` arm if 12f landed first (integration row 39); each walk makes one `PromptMode::default()`.
