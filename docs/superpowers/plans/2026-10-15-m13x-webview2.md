**Goal:** a person can make a Browser profile and open it as a tab, window or split pane that browses the web with Back, Forward, Reload, a URL bar that searches and suggests, bookmarks and history that Open Quickly finds, optional ad blocking and proxy, and Instant Replay; a script's dynamic toolbelt tool and HTML popover render their pages; Quick Look shows a link's page in a popover; clicking a link offers to open it in Tandem as iTerm2 does; an AI chat's list icon is drawn from the model's SVG.

**Architecture:** pure models first, each a plain `pub mod` tested on the Windows test machine without a web view. `webhost.rs` (pure) is the host's model: the runtime check's outcome, user data folders, environment options, the bridge's message and reply texts, bounds math. `webhost_win.rs` (`#[cfg(windows)]`) is the only file that touches COM: `Env` (one `ICoreWebView2Environment` per user data folder, created asynchronously and handed back through `pty::Notify`) and `WebView` (one `ICoreWebView2Controller` whose parent is a winit window's HWND, with its events queued as `webhost::Event`s the app drains in `about_to_wait`). Every caller holds a `WebView` and never a COM pointer. `web_popover.rs` is a borderless popup window (an `EguiHost` for the optional button row, a `WebView` filling the rest). `svg_icon.rs` (pure) extracts SVG candidates; `svg_raster_win.rs` (`#[cfg(windows)]`) renders one in a hidden `WebView` and captures 128 by 128 PNG bytes. The browser: `browser.rs` (pure: profile type, URL normalizing, the suggestion scorer, session titles, toolbar model, the upsell and open-link decisions), `browser_db.rs` (the `browserdb-<uuid>.sqlite` file in iTerm2's schema through 12c's `rusqlite`), `adblock.rs` (pure: WebKit content-blocker JSON compiled to a matcher), `web_replay.rs` (pure frame ring) and `web_replay_ui.rs` (the playback window). A browser pane is a `Pane` whose `Io` is the new `Io::Browser(BrowserIo)` (no pty; its screen is never drawn), so tabs, splits, focus, burying, titles, arrangements and the API keep working unchanged; the app keeps one `WebView` per browser pane in the app-wide `browser_views: HashMap<PaneId, BrowserView>` (keyed by pane, so it needs no `swap_live` entry; a view is re-parented when its pane changes windows). Dynamic tool views are per window (`WinSlot.tool_views`, listed in `swap_live`). The app side is `src/app/webhost_app.rs` (env lifecycle, the event drain, the bridge), `src/app/tool_web_ui.rs`, `src/app/web_popover_app.rs`, `src/app/browser_app.rs` (panes, toolbar, URL bar, menus), `src/app/browser_db_app.rs`, `src/app/web_replay_app.rs`.

**Tech Stack:** as milestones 12a to 12f plus one new crate: `webview2-com = "0.39.1"` (Microsoft's WebView2 COM API on the `windows` 0.62 crate already in the tree, `Cargo.toml:44`; the Decision in the Resume notes gives the reasons against the alternatives). ### Loader and dependency (Decision)

- `webview2-com` 0.39.1 (2026-03-11, MIT, by wravery, the crate `wry` and Tauri use) depends on `windows` and `windows-core` ^0.62, the same `windows` 0.62.2 already in `Cargo.lock`, so it adds only `webview2-com`, `webview2-com-sys` and `webview2-com-macros`; it gives typed interfaces up to `ICoreWebView2_28` and `ICoreWebView2Environment9`/`...EnvironmentOptions4`, plus completion-handler helpers. The alternative, "the WebView2 loader via windows-sys", has no bindings (the WebView2 metadata is not in `windows-sys`), so it means hand-written vtables for a dozen interfaces and every event handler: thousands of lines of unsafe code to review. `wry` itself is rejected: it owns the window and event loop.
- `webview2-com-sys` on MSVC links `WebView2LoaderStatic.lib` statically (`link_webview2!` in its `lib.rs`), so the loader code is part of `tandem.exe` and no `WebView2Loader.dll` exists to ship (the earlier `raw-dylib` reading was wrong). The non-MSVC build would import the DLL; Tandem builds on MSVC only.
- The runtime itself is the Evergreen WebView2 Runtime Windows installs and updates; Tandem never installs it. `BrowserPluginPathHint` maps to `browserExecutableFolder` (a fixed-version runtime), iTerm2's "location of the plugin if it cannot be auto-detected" (`AS:846`, `GW:170-185`).

### Host

- One environment per user data folder, created lazily. WebView2 refuses a second environment on the same folder with different options, so each `Store` has its own folder: `Default` (tools, popovers, Quick Look, icon rendering), `Browser` (browser panes, proxy arguments, the `iterm2-about` scheme), `DevNull` (Dev Null Mode; each of its views is InPrivate through `ICoreWebView2ControllerOptions.IsInPrivateModeEnabled`, since WebView2 has no environment-level InPrivate). iTerm2 uses the default website data store for tools and popovers (`TWV:57`, `WVW:139`) and a per-user store for the browser (`BM:204-212`), non-persistent for Dev Null.
- Controllers are children of a winit window's HWND. The UI thread is winit's; winit initializes OLE (an STA) on it, which WebView2 requires; asynchronous completion handlers run from that thread's message pump, which winit runs. Never call webview2-com's `wait_with_pump` helper in the app (it pumps messages re-entrantly inside a winit callback; 0.39.1 has no `wait_for_async_operation`); ignored tests may use it (Task 1).
- A child window cannot be covered by anything the wgpu scene draws: in-scene popups (autocomplete, the Composer, find bars) under a web view are hidden by it. Tandem keeps in-scene popups out of browser panes (they have none) and tool areas (none open there); a muda menu or an `EguiHost` window is a separate top-level window and shows above.
- Keys: while a web view has focus, winit gets no key events. `AcceleratorKeyPressed` reports every key with modifiers; Tandem posts `Event::Key` and, when `keyroute` finds a Tandem menu shortcut or key binding for it, marks the event handled and runs it (iTerm2's key bindings keep working in a browser, `iTermBrowserKeyBindingActionPerformer.swift`); plain typing stays with the page.

- `02:704` SearchCommand is used by the context menu's "Search the Web for Selection" too (`CMH:1179-1186`), not only by browser sessions; `02:705` only by the URL bar.
- `NoSyncOpenLinksInApp` is not a plain preference: the settable bool shares its key with the permanently silenceable warning, so the Advanced row and the ask's "do not ask again" are the same value (`WS:398-406`, `iTermBrowserSettingsHandler.swift:566-620`).
- The Browser session keys `Dev Null Mode` and `Browser Zoom` have no parity rows; Task 11 adds them.
- Quick Look of a URL is an 800 by 600 popover with an "Open in <browser>" button, not a bare web view.
- The research's "WebView2 has no content worlds" holds only for `AddScriptToExecuteOnDocumentCreated` and `ExecuteScript`, which run in the page's world; the DevTools protocol gives WebView2 isolated worlds (`Page.addScriptToEvaluateOnNewDocument` with `worldName`, `Runtime.addBinding` with `executionContextName`), which 13x2 uses for iTerm2's `.defaultClient` scripts (R13x23-1). This plan injects nothing that needs one.

### Decisions (each goes in `m13x-rulings.txt`)

- WebView2 through `webview2-com` 0.39.1 (reasons above), its static loader linked into the exe. Cost: an SDK bump is a crate bump.
- Three user data folders under `%LOCALAPPDATA%\Tandem\WebView2` (Default, Browser, DevNull). Cost: tool and popover pages do not share cookies with browser sessions (iTerm2's defaults store is shared by tools and popovers and separate from the browser user's store, so this matches except Quick Look).
- Browser panes use WebView2's own user agent plus "Tandem", not iTerm2's Mac Safari string. Cost: sites see Edge.
- A proxy change closes and recreates every browser view (each reloads its URL). Cost: unsaved form input in open pages is lost.
- Content blocking is Tandem's matcher over WebKit's JSON through `WebResourceRequested`; block-cookies and make-https are ignored. Cost: slower than WebKit's compiled lists; two action types unsupported.
- Suggestions and the ad block list use 12b's WinHTTP transport with the system proxy (not the browser proxy). Cost: a person who relies on the browser proxy for privacy still sends typed queries to the search provider directly, as iTerm2 does.
- Back and Forward long-press lists come from Tandem's own per-pane navigation list. Cost: a page's `history.pushState` entries may not all appear.
- Browser Instant Replay keeps JPEG frames captured at up to the frame rate and saves Motion JPEG AVI (m13 rulings, 13x/13y). Cost: larger memory per second than H.264; the rate is not guaranteed.
- Tandem is never the Windows default browser, so the "we are the default browser" branch never applies. Cost: none until 13v registers protocol handlers.
- Welcome page actions outside this plan's scope answer nothing. Cost: those buttons do nothing.
- The browser database creates only the history, bookmark and visit tables. Cost: an iTerm2 database copied over keeps its other tables unused.
- `Io::Browser` panes answer the API's job name "Browser" and are excluded from broadcast and tmux. Cost: scripts see a fixed job name.
- The toolbar is 32 points tall and uses Segoe Fluent Icons glyphs instead of SF Symbols. Cost: a different look.
- The popover's semitransient close reads the foreground window. Cost: none known.
- Focus moving into a Tandem-owned web view is not a window focus loss; a terminal pane gets its DECSET 1004 focus-out only when a browser pane in the same window takes focus (R13xy-4). Terminal-to-terminal pane changes are 13y2 Task 9d's (the R13xy fix pass ruling: built, 1:1 with `PTYTab.m:951-960`), so this plan leaves them as they are. Cost: none once 13y2 lands.
- Chat icons render in a hidden WebView2 `<img>` (script never runs inside the SVG). Cost: no icons without the runtime.
- Tests that need the runtime are ignored and skip when it is missing. Cost: CI does not exercise COM paths.
- The host carries the follow-up plans' needs from the start (M13 integration pass): response headers, message sources, the navigation URL and id on `Navigated`, the local-scheme navigation guard with `navigate_tandem`, the proxy host check and `event_loop` on `web_tick`/`browser_event`. Cost: 13x ships a few fields and one rule that only later plans exercise fully.
- The proxy host must be a plain hostname, IPv4 or bracketed IPv6 address (Tandem's check; iTerm2 checks only for empty). Cost: a host written with a port or a scheme is refused (the proxy is off until corrected).

### Pitfalls for the implementer

- Never call webview2-com's blocking `wait_with_pump` outside tests; every completion handler posts to the channel and wakes the loop with `Notify`.
- Lib tests that link the raw-dylib loader import still start under `cargo test`: cargo puts build-script link-search paths inside `target/` on PATH, and `webview2-com-sys`'s `OUT_DIR/x64` holds the DLL.
- A child HWND takes keyboard focus: winit sends `Focused(false)` to the parent even though the window is still active. Popover close and "window has focus" logic must read `GetForegroundWindow`/`GetAncestor(GA_ROOT)`, not winit focus; the App's own focus arm goes through Task 1a's `focus_step`, and a held focus is re-checked on `Event::Focus(view, false)` and every `web_tick`, because the real deactivation sends the parent nothing.
- Bounds are physical pixels in the parent's client coordinates; recompute on every layout, scale change and window move between monitors (`WM_DPICHANGED` reaches winit as `ScaleFactorChanged`).
- Hidden tabs: `put_IsVisible(false)` stops rendering; keep capture ticks off for hidden browser panes.
- `NavigateToString` is limited to 2 MB: a larger popover HTML shows the text popover fallback with a log line.
- `WebResourceRequested` for "*" sees every request of a browser page: take `GetDeferral` in the handler, post the event, return at once, and complete the deferral in `answer_request` from `web_tick` (the matcher is in-memory and bounded by Task 8's timing test). A view closed with requests pending completes them with `Continue`.
- COM strings from WebView2 are `CoTaskMemFree`d by `webview2-com`'s helpers; do not free them twice.
- The loader is static: there is no `WebView2Loader.dll` to copy; a missing runtime (not the loader) is the `Runtime::Missing` case.
- Do not pass `file:` URLs from pages to `ShellExecute`; a download or a `file:` navigation stays inside WebView2.
- `rusqlite` is 12c's; do not add a second SQLite crate or a second copy of the bundled library.
