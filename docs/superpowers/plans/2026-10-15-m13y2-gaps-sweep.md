### Signed archives

- Format (`SAC:14-45`, `SAR:33-176`): a sequence of chunks, each an 8-byte big-endian tag, an 8-byte big-endian length (both must be non-negative) and the payload; tags header 0, payload 1, metadata 2, signature 3 (deprecated), certificate 4, signature2 5. The header chunk must be first and hold "signed-archive". Metadata is UTF-8 `key=value` lines; known keys `version` and `digest-type` (`SIGArchiveCommon.m:14-24`); a repeated known key is malformed; rows without "=" are skipped (`SAV:170-200`). Version must be 2 (1 is deprecated, above 2 too new, `SAV:203-230`); digest "SHA2" (`SAV:232-248`). Certificates: every certificate chunk, leaf first (`SAR:114-131`). Signature2 signs every byte from the start through the end of the chunk before it and must be the last chunk (`SAR:146-167`). Verification: `SecTrustCreateWithCertificates` with the basic X.509 policy and a CRL revocation policy, evaluated (`SAV:300-330`, `ST:20-79`, `SP:15-64`); then `kSecKeyAlgorithmRSASignatureDigestPKCS1v15SHA256` with the leaf's public key over the SHA-256 digest (`SV:22-98`). Author: the certificate's common name, else its long description, else "Unknown" (`SC:62-80`, `IM:266-270`).
- Import flow (`IM:157-270`): `.its` that does not smell like an archive answers "This script archive is corrupt and cannot be installed."; verification errors answer the verifier's text (or "Unknown error"); a requireSignature import (not user-initiated) of anything else answers "This is not a valid iTerm2 script archive."; after verification with a signature required: the certificate data checks (`CERT_NIL`, `CERT_BAD`), the confirmation "Confirm Installation" (persistent) with OK, Cancel, Reveal Contents; Cancel answers "Installation canceled by user request." quietly; OK copies the payload to a temp `.zip` and installs it trusted; Reveal installs to a temp location and reveals. User-initiated imports of `.its` still verify (`IM:97`, `requireSignature:!userInitiated` only affects non-`.its` files).
- Trusted AutoLaunch (`AR:138-230`): a trusted archive whose metadata says `AutoLaunch` asks "\u{201c}%@\u{201d} would like to launch automatically when iTerm2 starts. Would you like to allow that?" (heading "Allow Auto-Launch?", buttons "Launch Automatically", "Lauch Manually"); an explicit offer uses "\u{201c}%@\u{201d} can launch automatically when iTerm2 starts. Would you like to allow that?".
- Windows mapping: `CertCreateCertificateContext(X509_ASN_ENCODING, der)`; an in-memory store (`CertOpenStore(CERT_STORE_PROV_MEMORY)`) holding the intermediates; `CertGetCertificateChain(NULL engine, leaf, NULL time, store, &{ cbSize, RequestedUsage = none }, CERT_CHAIN_REVOCATION_CHECK_CHAIN, ..)` in the app; in tests (R13xy-14) a chain engine from `CertCreateCertificateChainEngine` whose `CERT_CHAIN_ENGINE_CONFIG.hExclusiveRoot` is a memory store (empty for the untrusted case, holding the test root for the trusted case) and the flags `CERT_CHAIN_REVOCATION_CHECK_CACHE_ONLY | CERT_CHAIN_CACHE_ONLY_URL_RETRIEVAL | CERT_CHAIN_DISABLE_AUTH_ROOT_AUTO_UPDATE`, so neither AIA, CRL nor the automatic root update is fetched; `CertVerifyCertificateChainPolicy(CERT_CHAIN_POLICY_BASE)` and the chain's `TrustStatus.dwErrorStatus == 0`; `CryptImportPublicKeyInfoEx2(X509_ASN_ENCODING, &leaf.pCertInfo.SubjectPublicKeyInfo, 0, NULL, &key)`; `BCryptVerifySignature(key, &BCRYPT_PKCS1_PADDING_INFO{BCRYPT_SHA256_ALGORITHM}, digest, 32, sig, len, BCRYPT_PAD_PKCS1)`; `CertGetNameStringW(leaf, CERT_NAME_ATTR_TYPE, 0, szOID_COMMON_NAME, ..)`. All in `windows-sys` `Win32_Security_Cryptography`.

### Pitfalls for the implementer

- Parse `.its` lengths with checked arithmetic; a crafted length near `u64::MAX` must not wrap or allocate.
- Never extract or move anything from an `.its` payload before verification and confirmation; Reveal Contents extracts to a fresh temp folder only.
- The self-signed test certificate's private key must be created in a test-only key container and deleted even when the test fails (a `Drop` guard).
- `BCryptVerifySignature` returns `STATUS_INVALID_SIGNATURE` for a mismatch; map it to `SignatureDoesNotMatchPayload`, other codes to `IoRead`-class errors with the code in the log.
- The LastPass stdin must stay open while waiting for the answer; closing it early makes `lpass` read EOF and fail.
- Adapter binaries must not link the GUI: keep their `use` of `tandem` to pure modules (`pwm_*`, `ai_transport`, `ai_winhttp`), so they start fast and need no window.
- The audit reads docs through `include_str!`; `scripts/xt` syncs `docs/`, so the test sees the edited files.
