Posts: find-global-click.js:21 {type:'iTermGlobalClick', clickData:{offset, textContent, coordinates}} to window.parent; find-engine.js:753 and :786 {type:'iTermIframeClick', frameId, clickLocation, framePath} to window.parent (the second forwards one). Findings: (1) no message holds the view secret or any secret: sessionSecret appears only inside the find script's own constant and the Client bridge post (a DevTools binding of the isolated world, never a window message); find-engine.js logs it through console.debug, which the isolated world's console wrapper only counts. (2) The page world and any cross-origin frame can READ these messages (frame ids, the clicked text node's text, coordinates; all page content anyway) and FORGE them (they carry no secret); a forged one can only change the stored click location, that is where the next match search starts, or push a click notification up the frame chain. It cannot run code, reach a native handler, or open anything. (3) find-nav.js:587 listens to keydown on the document with no isTrusted check, so a page can pick a navigation bubble with synthetic keys once the person has turned shortcuts on; the pick ends in window.open(url, '_blank', 'noopener,noreferrer') (find-engine.js:1917), which WebView2 reports as NewWindowRequested with IsUserInitiated false for a synthetic event, and webhost::NewWindowLimiter::allow refuses anything not user-initiated, so no Event::NewWindow and no tab follows. Nothing is edited in the copied files (they are never edited); the probe test find_messages_forged_by_a_page (webhost_win::probe, desktop only, picked up by probe-desktop.ps1's default filter) checks the secret never reaches the page world, no window opens, and find still answers after the forgeries - cost if wrong: a page misplaces the start of the next find or reorders which match is current; if the NewWindow gate were ever relaxed, a page could open tabs by synthetic keys while bubbles are showing.
