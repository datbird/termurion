m13u rulings (keys and hotkeys)

Task 6: Respect shortcuts from Windows keyboard shortcuts (02:340, R3, R7)
- Tandem's hook took shell chords for key mappings; iTerm2's default (Respect shortcuts from System Settings) lets the system's shortcuts win. Fixed (R3) under ruling R7: with AllowSymbolicHotKeys on (default), a key mapping on a Win chord the shell keeps (winkeys::shell_owned_chord) no longer takes it from Windows.
- Stock global shortcuts are Tandem's own; R7 yields only the person's own mappings (a global entry byte-for-byte equal to schema/keymaps.toml [global] is stock; an edited or profile mapping is the person's). Cost if wrong: Win+Left would snap the window instead of changing tab, from the keyboard and from bumbles.
- A Tandem menu command (commands::command_for_chord) never yields. The Leader, Win+number and composer chords are not key mappings and never yield.
- shell_owned_chord is pure (a scan table over menus::Chord, U.S. layout independent), so the hook thread makes no Win32 call per keystroke.
- Cost if wrong (R7): a user mapping on a shell chord with no Tandem command (Win+B, Ctrl+Win+B) needs the option off. Note Win+E and Ctrl+Win+Left are Tandem menu commands, so they stay Tandem's.
- Session hotkeys (Task 8, B3, B4): a hotkey works in every app, so only the person's own choice registers. One set from the Edit Session row (App::set_session_hotkey), or allowed in the "Register a hotkey?" question (NoSyncSessionHotkeyFromProgram, Permanent; only Ignore is remembered), is live. A value a program wrote (set_session_values, a tmux server's @hotkeys) is stored with its session and inert. Cost if wrong: a person's own hotkey restored from an arrangement asks once more.
- Session chords need Ctrl, Alt or Win, are never a chord Windows keeps (winkeys::shell_owned), never equal the app, Open Quickly or a profile hotkey, and at most 16 are on. @hotkeys is written only for what the person set or allowed and read bounded (4 KiB, 64 entries, 64 bytes of text each). Cost if wrong: a tmux-held hotkey nobody allowed is dropped from the server's option on the next write.
- Session ids are SESSION_HOTKEY_BASE + group index, routed before the previous-window tail; a refused chord's error shows on each of its sessions' rows.
- Entries of Tandem's own key mapping presets (Natural Text Editing's Win+Left and Win+Right) count as stock too while unedited: a profile entry byte-for-byte equal to a preset's entry never yields to Windows. Cost if wrong: a person who wants Windows' snap on those keys must edit or remove the mapping.
- winkeys::shell_owned (R7's list, also the session hotkey rule) covers Windows 11's Win+Ctrl+Space, Q, N, S, V, 1-9 and Win+Alt+1-9, and matches Win+Shift exactly (S, M, V, T, Space, digits, Left, Right, Up; Win+Ctrl+Shift+B) as iTerm2's symbolic hotkeys match modifiers exactly, not every Win+Shift+letter. To confirm on EXTREME (not added): Win+Alt+Up/Down (snap halves) and Win+Ctrl+O (On-Screen Keyboard). Cost if wrong: a mapping on a chord Windows does not consume yields needlessly (the key still reaches Tandem).

Task 9: fading hotkey windows (01:297, 03:668, B2)
- Probe result (Step 0, src/fade_probe.rs, ignored test, run over ssh on EXTREME, wgpu Vulkan on the Intel UHD 770 adapter of the shared instance): a cloaked, off screen, never-activated tool window presents three frames without an error before the layered style, with WS_EX_LAYERED + LWA_ALPHA 128 (GetLayeredWindowAttributes reads 128), and after the style is removed. The color readback could NOT be made: ssh runs in session 0, which has no composed desktop, so PrintWindow reads black even for the baseline, and a second SetLayeredWindowAttributes on a window fails there (error 31). wgpu's DX12 surface would not configure on that window and a second device on the NVIDIA Vulkan adapter crashed the process; neither was investigated. So FADE_LAYERED is true on the evidence "no present error, attribute applies", with the run-time safety net (a refused attribute or a present error stops fading for the run), and the visual check is a checklist item that needs Robert's desktop session. Cost if wrong: an opaque-surface hotkey window shows blank for the fade's 0.25 s, or never fades.
- FADE_COMPOSED (B2): the see-through hotkey window (13g's DirectComposition alpha window) cannot take a layered style. The renderer scales the whole premultiplied target in a last pass (Frame.fade, default 1.0; blend src Zero, dst Constant, set_blend_constant). Proven on the shared test device (render::tests::fade_scales_the_premultiplied_target: 0.5 reads half in all four channels); the DirectComposition present itself needs the second (DX12) instance, which tests may not make, so it is a checklist item. Cost if wrong: the see-through window pops instead of fading.
- fade_path(alpha_surface, layered_ok, composed_ok, present_failed) replaces the plan's fade_allowed. An alpha-surface window that is not drawing see-through (opaque alpha mode) does not fade (scaling would darken it). A window recreated during a fade ends the fade (shown at once, a slide still finishes).
- Pacing: edge styles ease in (position and opacity together); a fade with no slide (left, normal, centered, maximized, or an edge whose hidden frame lies on another monitor) is linear. Full screen does not fade. With "Animate hotkey window" off nothing is touched. The 8 ms Roll tick drives every fade and ends with the roll (no idle wake, P17).
- A composed show renders one frame at opacity 0 before the window is uncloaked, so the last frame it hid with never flashes. Cost if wrong: one extra frame draw per show.
