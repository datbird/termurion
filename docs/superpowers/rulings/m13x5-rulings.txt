m13x5 rulings (browser marks and triggers)

R13x5-1 (Task 1 name mapping, B4): navigate_script / show_script became navigate_call / show_call, returning Call { body, args }; page-derived values travel as typed arguments (xpathArg, textFragmentArg, marksArg), never in script source.

R13x5-2 (Task 2): the table is bounded. Caps::named_marks 20_000 (a full table refuses the new mark, nothing is deleted); guid <= 128, URL <= 8192 bytes with no control character, text <= 2048 chars, name cleaned with inert_files::display_text and cut to 256 chars. Every read drops a row that breaks a bound (corrupt or oversized data loads empty). MAX_XPATH is 2048 (B8). MAX_MARKS 1000 stays the per-page annotation cap. The URL lookup and the page-first ordering never treat the page's "_" or "%" as wildcards (escaped LIKE / SUBSTR compare); iTerm2 pasted them raw (BNM:158-166). Saved marks carry no Imported column (the schema is iTerm2's, byte for byte); a mark never navigates or runs script without the person's action.

R13x5-3 (task-1 review, important 1): the layout monitor must be running in the isolated world before any update-mark-positions run (the script calls iTermLayoutChangeMonitor.reenableLayoutChangeMonitoring and throws without it). Task 4 follows this order after every navigation and after every world rebuild (browser_world_restart). The probe now starts the monitor first.

R13x5-4 (task-1 review, important 2, B2): the annotation box is built in a closed shadow root created in the isolated world (host id iterm-mark-annotations; the root is window.tandemMarkRoot, isolated world only; update-mark-positions.js reads from it). Save and Delete act only for a trusted event aimed at the real button: a pointer click needs shadow.elementFromPoint(clientX, clientY) === the button, a keyboard activation (detail 0) needs that button focused, and Enter in the input is trusted-only. All patches are exact-once and fail closed. Residual: a page can still hide, move, resize or transform the host element, or delete it (the person then sees no annotation, or an annotation displaced on screen); it cannot read the name, press the buttons, or post a rename or delete. Position updates still read data attributes inside the shadow root, which a page cannot reach, so their answers are page-independent; Task 4 still validates them (valid_position_updates).

R13x5-5 (Task 3, B5, B10, P5, epoch): adding is only ever a person's action (Edit menu, the page context menu pick, the Named Marks tool's Add) and never because a page asked. Tandem's own iterm2-about: pages take no mark by any path (Refusal::Local). The method comes from a second WebResourceRequested handler on a Document-context filter (no deferral); the first handler skips a Document request that only that filter matched, so no navigation takes the answer_request round trip it did not before. Event::DocumentMethod carries the navigation id (nav) of the last main-frame NavigationStarting and is applied only to that navigation (P5); the method is bounded (16 token characters, else "UNKNOWN", which no add accepts). The method, the epoch (bumped by every main-frame Starting and every world reset) live in BrowserView (B3); a prompt carries the epoch it began in and the mark is stored only if the epoch is unchanged after OK and again after the page answers. The page's centre and XPath answers are validated (finite integers in range, Location::from_json, mark_url within MAX_URL) before anything is stored. An XPath holding "&" is refused (the fragment is split on "&" and the fragment encoding keeps it, so the page could write its own textFragment pair; task-1 re-review minor 5); iTerm2 writes it raw.

R13x5-6 (supersedes the residual of R13x5-4; task-1 re-review, B2 class fix): any in-page control can be clickjacked (opacity, pointer-events decoys) and the page sees the keys typed into the page, so the in-page annotation box is display plus two buttons that only REQUEST an action: "Rename" posts {guid, requestRename, sessionSecret} and "Delete" posts {guid, requestDelete, sessionSecret}; nothing is renamed or removed in the page; the name input is a hidden field that takes no key; update_of honors no message that carries a name or a delete. The name is typed in, and a delete confirmed by, a Tandem window outside the web view (Task 5), which the page cannot see, cover or type into. Truthful residual: a page can hide, move or delete the box or lure the person into pressing Rename or Delete; the worst result is that Tandem's own window opens (a delete always asks natively, a rename takes only what the person types there). It cannot read a name (the root is closed; names are not in the page's text) or change a mark. The host is styled inline with all: initial and !important rules (page CSS cannot displace it) and the previous box is removed by the reference Tandem keeps (window.tandemMarkHost), never by a page-controlled id; the host carries no id.
