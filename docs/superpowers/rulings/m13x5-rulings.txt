m13x5 rulings (browser marks and triggers)

R13x5-1 (Task 1 name mapping, B4): navigate_script / show_script became navigate_call / show_call, returning Call { body, args }; page-derived values travel as typed arguments (xpathArg, textFragmentArg, marksArg), never in script source.

R13x5-2 (Task 2): the table is bounded. Caps::named_marks 20_000 (a full table refuses the new mark, nothing is deleted); guid <= 128, URL <= 8192 bytes with no control character, text <= 2048 chars, name cleaned with inert_files::display_text and cut to 256 chars. Every read drops a row that breaks a bound (corrupt or oversized data loads empty). MAX_XPATH is 2048 (B8). MAX_MARKS 1000 stays the per-page annotation cap. The URL lookup and the page-first ordering never treat the page's "_" or "%" as wildcards (escaped LIKE / SUBSTR compare); iTerm2 pasted them raw (BNM:158-166). Saved marks carry no Imported column (the schema is iTerm2's, byte for byte); a mark never navigates or runs script without the person's action.

R13x5-3 (task-1 review, important 1): the layout monitor must be running in the isolated world before any update-mark-positions run (the script calls iTermLayoutChangeMonitor.reenableLayoutChangeMonitoring and throws without it). Task 4 follows this order after every navigation and after every world rebuild (browser_world_restart). The probe now starts the monitor first.

R13x5-4 (task-1 review, important 2, B2): the annotation box is built in a closed shadow root created in the isolated world (the host carries no id: R13x5-6 supersedes this ruling's host id and Enter clauses and its residual; the root is window.tandemMarkRoot, isolated world only; update-mark-positions.js reads from it). Save and Delete act only for a trusted event aimed at the real button: a pointer click needs shadow.elementFromPoint(clientX, clientY) === the button, a keyboard activation (detail 0) needs that button focused, and Enter in the input is trusted-only. All patches are exact-once and fail closed. Residual: a page can still hide, move, resize or transform the host element, or delete it (the person then sees no annotation, or an annotation displaced on screen); it cannot read the name, press the buttons, or post a rename or delete. Position updates still read data attributes inside the shadow root, which a page cannot reach, so their answers are page-independent; Task 4 still validates them (valid_position_updates).

R13x5-5 (Task 3, B5, B10, P5, epoch): adding is only ever a person's action (Edit menu, the page context menu pick, the Named Marks tool's Add) and never because a page asked. Tandem's own iterm2-about: pages take no mark by any path (Refusal::Local). The method comes from a second WebResourceRequested handler on a Document-context filter (no deferral); the first handler skips a Document request that only that filter matched, so no navigation takes the answer_request round trip it did not before. Event::DocumentMethod carries the navigation id (nav) of the last main-frame NavigationStarting and is applied only to that navigation (P5); the method is bounded (16 token characters, else "UNKNOWN", which no add accepts). The method, the epoch (bumped by every main-frame Starting and every world reset) live in BrowserView (B3); a prompt carries the epoch it began in and the mark is stored only if the epoch is unchanged after OK and again after the page answers. The page's centre and XPath answers are validated (finite integers in range, Location::from_json, mark_url within MAX_URL) before anything is stored. An XPath holding "&" is refused (the fragment is split on "&" and the fragment encoding keeps it, so the page could write its own textFragment pair; task-1 re-review minor 5); iTerm2 writes it raw.

R13x5-6 (supersedes the residual of R13x5-4; task-1 re-review, B2 class fix): any in-page control can be clickjacked (opacity, pointer-events decoys) and the page sees the keys typed into the page, so the in-page annotation box is display plus two buttons that only REQUEST an action: "Rename" posts {guid, requestRename, sessionSecret} and "Delete" posts {guid, requestDelete, sessionSecret}; nothing is renamed or removed in the page; the name input is a hidden field that takes no key; update_of acts on no name or delete field (it reads only guid, sessionSecret and the two request flags). The name is typed in, and a delete confirmed by, a Tandem window outside the web view (Task 5), which the page cannot see, cover or type into. Truthful residual: a page can hide, move or delete the box or lure the person into pressing Rename or Delete; the worst result is that Tandem's own window opens (a delete always asks natively, a rename takes only what the person types there). It cannot change a mark. That it cannot read a name rests on the closed root and on names not being in the page's text; the probe assertions for it (innerText, window.find, a select-all selection read) are written but UNVERIFIED until the probe runs in the console session. The host is styled inline with all: initial and !important rules, so page CSS aimed at the host cannot restyle it; styles on its ancestors (opacity, filter, transform, display on body or html, a positioned body) can still hide or move it, because it is position: absolute, not fixed in the top layer. The previous box is removed by the reference Tandem keeps (window.tandemMarkHost), never by a page-controlled id; the host carries no id.

R13x5-7 (task-3 review): the method of a navigation is told once: MethodState::document accepts the first document request of a navigation and ignores any later one (first request wins; that an iframe loading the page's own URL cannot change it holds only if WebView2 raises the main document request first, which is unverified until document_method_is_reported runs in the console session). A "&" in a page's text fragment is stored as "%26" in the text layer ("%2526" in the URL) and read back as "&", so page text cannot write a pair of its own; the XPath still refuses it. A same-document URL change between a request and its answer (pushState, no Starting, no epoch bump) stores the mark under the page's new URL, as iTerm2 reads webView.url.

R13x5-8 (Task 4 review): marks_modify_dom takes a typed Call, not body: String (B4, R13x5-1). The layout monitor disables itself before every post, so a layout message the 1 s gate refuses, or that arrives when the page has no cached mark, only re-enables the monitor (never dropped silently). The modify-DOM chain checks the navigation epoch at every async step, and a world rebuilt under a loaded page starts the monitor, then the annotations (R13x5-3).

R13x5-9 (Task 5): rename and delete run in Tandem windows outside the web view: the name entry is the shared prompt window (PromptWindow), the delete confirm is ConfirmWindow (Cancel is the default; only Delete removes). A request is refused for a mark Tandem does not know, one not on this pane's page, or one from an older navigation epoch; the check repeats at open and at answer. The window shows only the stored name through inert_files::display_text, is one per pane, ignores keys and clicks for 500 ms after opening (no 13x6 permission prompt exists on this branch to share a guard with), and is closed with no change by the next main-frame start or by the pane closing. A reveal is bound to the navigation that started it (B9): the first Tandem-made main-frame start after it, followed through redirect hops; any other start, or a rebuilt world, drops it; a failed load keeps it until then. Its URL passes browser_restore::load_gate and goes through browser_navigate. The pending reveal lives in the view's PageState (B3), not in an App map. Removing the last mark of a page clears the annotation host by Tandem's reference (the show script returns early on an empty list). The monitor re-enable after a navigation that never completes is balanced: the monitor counter is clamped at 0 by a load-time patch (R13x5-11), so an enable with no disable outstanding is harmless.

R13x5-10 (Task 7, B7, trigger security): page text matching a trigger is untrusted and never the person's consent. Import classification of the eight browser classes (and the three bare synonyms): IMPORT_ENABLED, inert (they only draw): Highlight Text (colors pass css_color, which admits only "#rrggbb" and the exact p3 form, so no stored text reaches CSS) and Make Hyperlink (the link is clicked by the person; a new window goes through nav_gate_tab, same as the terminal Hyperlink trigger). IMPORT_OFF: both Inject Javascript (run script in the page), Reload After Delay (a page-paced reload loop), Enter Reader Mode (changes what the person sees on a page's say-so), Enter Workgroup and Exit Workgroup (start or end commands and sessions; they also go through the 13y1 queue and approval, Task 10). Enter Reader Mode and the two workgroup actions carry later: Some(13) until Task 10. trigger_file::every_catalog_class_is_classified now covers BROWSER_CATALOG and BROWSER_SYNONYMS, and import_description names browser actions by title. triggers_of drops browser actions for terminal panes and returns nothing for a browser pane.

R13x5-11 (Task 5 re-review, amends R13x5-9): the layout monitor's enable/disable counter never goes below 0. layout-change-monitor.js rebuilds its observer only when the counter is exactly 0, and marks_reenable (a navigation that never completed) sends an enable with no disable outstanding, which left the counter at -1 and the observer gone for good. monitor_body applies an exact-once, fail-closed patch ("disabledCount -= 1;" becomes a clamped decrement); when it does not apply, the monitor is not started and a line is logged. marks_reenable still sends enable unconditionally, which is now safe. The copy of the file is unchanged (the patch is at load).
