m13v2 rulings (updates, tips, accessibility)

Task 2: checking for updates
- P1 (notify only): the update path never downloads, installs or replaces anything. The trust root is TLS to api.github.com checked by curl's schannel; the feed yields a version string, one pinned release-page URL and body text shown as plain text. Source tests pin it (update_never_downloads, one_curl_start_and_no_download). Entry gate for any later install milestone: EdDSA-signed feed with a key built into Tandem verified before any version is trusted; signature AND SHA-256 verified before run; Authenticode on the installer; a per-user %LOCALAPPDATA% download folder with an owner-only DACL and the verified file opened by handle (no TOCTOU); the person's click per update; never runas silently; harden_process-covered launch. Cost if wrong: a compromised GitHub account or TLS-intercepting CA can only show a false "update available" and a text body; adding a download without the gate would be code execution.
- P2/B4 (the fetch): curl.exe from System32 (RealRunner::system_tool), run in its own Job Object, hidden, never through a shell, stdin empty, cwd the System32 folder, environment without CURL_CA_BUNDLE, SSL_CERT_FILE, SSL_CERT_DIR, CURL_HOME and CURL_SSL_BACKEND (proxies stay curl's own), arguments exactly update::fetch_args (-q first, --proto =https, --proto-redir =https, no --fail). stdout is capped at 2 MiB plus the status line (past it curl is ended: "feed too large"); a 35 s cap ends a slow one. Cost if wrong: behind a TLS-inspecting proxy whose CA is not in the Windows store a manual check shows "Update Error!" (nothing in the background).
- One request at a time on a worker thread (never on the UI thread); Cancel and quitting end the running curl (update_fetch_win::cancel_running, called by teardown_process); a cancelled answer is dropped. Cost if wrong: none.
- Learn More opens only the pinned releases page or a path under it, through semantic::guard_open (update::release_url first). Cost if wrong: a release whose html_url is on another host opens the pinned page instead.
- SULastCheckTime is stored when a check starts (Sparkle SUUpdater.m:382, which overrides the brief's "a cancelled check must not push the schedule") and again after every finished check, a failed one or one with no information too (a failing feed never re-checks at every tick); a Cancel or a quit mid-check leaves the time from the start, so the next tick does not repeat the request at once. The schedule is the deadline in update_due that about_to_wait waits for; there is no poll. Cost if wrong: none.
- The Sparkle permission question is never silenceable (no id) and, closed with no button, stores nothing (it asks again on a later launch). SUHasLaunchedBefore is stored at the first launch ever; the question shows from the second launch. Cost if wrong: none.
- Decision: the permission question is queued as a capped ask so a flood cannot grow the queue past 16 (P21).
- Decision: a manual check while an update is already on offer brings that window forward and starts no new check. Cost if wrong: the person waits for the next scheduled check to see a newer release.
- Decision: the sink sweep (semantic_ui NOT_PANE_TEXT) lists update_fetch_win fetch, update_app learn_more_target and learn_more with their reasons (P20).
- Decision: SSLKEYLOGFILE is dropped from curl's environment with the other trust variables (System32 curl is Schannel-only, so it was inert; dropping it means a planted variable can never make curl write TLS session keys to a file). Cost if wrong: none.
- Ruling (Task 6, B2): this task SUPERSEDES the m13t Task 8 ruling (m13t-rulings.txt line 88, "Tandem never writes dynamic profiles back"). Settings_keys::dynamic_profile_spec (13t's built warning) is edited to iTerm2's full text and buttons (Mark as Rewritable, Reveal in Explorer never remembered, Cancel; id NoSyncDynamicProfileChangeWillBeLost, Kind::Temporary), and returns None for a saved or a rewritable profile. No second warning and no Then::DynamicProfileWarning exist. Cost if wrong: none.
- Decision (Task 6): one SheetThen::DynamicProfile(guid) carries both buttons (0 Mark, 1 Reveal) and the window hands the app a DynamicRequest after the frame. The warning shows on the first edit of each profile in a Settings window (iTerm2 asks on every edit that follows an answer; the ten-minute silence applies). Cost if wrong: a person who cancels is not asked again in that window.
- Decision (Task 6, B7): a write-back re-resolves the file below the folder (no "..", root or drive), applies the network judge, refuses a link at the file or any folder below the Dynamic Profiles folder and a file with more than one name, compares size, modified time and an FNV-1a hash of the bytes with what the load read (a mismatch writes nothing and logs "changed on disk, not rewritten"), writes a hidden ".<name>.tandem-tmp" made new in the same folder then renames it over the file, and ends with one reload. The file watch's own event for the write causes a second reload that changes nothing and shows nothing. Edits write 500 ms after the last one (a drag edits every frame). Non-object entries in a rewritten file are dropped. Cost if wrong: an edit made while the file changed on disk is shown as the file's own value after the reload.
- Decision (Task 6): the error alert is queued once per burst; errors that come while one waits are logged and counted (dynamic_errors_pending). "Reveal in Explorer" in that alert is never remembered, like View Log. A closed alert is no answer. Cost if wrong: none.
- Decision (Task 6): the watch is a worker thread blocked in the kernel; it wakes the app only when a reload is due (latency after the last change, never later than 5 s after the first change of a burst). A folder that goes missing is looked for every 5 s by the worker alone. The one process teardown stops every watch (dynamic_profiles_scan::stop_all). The folder is resolved once at start. Cost if wrong: none.
- Decision (Task 6): a changed Command, Custom Command, Initial Text or Triggers on a Guid already loaded is logged to the Dynamic Profiles entry (P8). A removed profile's running sessions keep their settings on a session copy made before the removal.
