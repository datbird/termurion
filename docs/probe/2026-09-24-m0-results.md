## Findings

### Legacy mouse encoding breaks past column 95 (both ConPTY copies)

The first run of `wsl-1000-legacy-col150` failed under both copies. Tandem sent
`1b5b4d20b726` (a click at column 151 in legacy, non-SGR, encoding). The app received
`1b5b4d20efbfbd26`. ConPTY replaces every input byte above 127 with U+FFFD, so a legacy
position past 95 (95 + 32 = 127) reaches the app as garbage.

Change: the encoder now sends nothing for a legacy position past 95. The row now checks
that. vim, tmux, and htop all turn on SGR mode (1006), which has no such limit, so this
only affects old apps that never ask for SGR.

### The Windows copy of ConPTY can hang on close after an early resize

`pty::tests::resize_succeeds` hung under the Windows (inbox) copy during a full test run.
A stress loop isolated it:

| Case (inbox copy) | Runs | Hangs |
|---|---|---|
| Resize right after start, then close | 8 and 1 (two loops) | 1 each loop |
| Close right after start, no resize | 120 | 0 |
| Resize after the shell printed output, then close | 40 | 0 |
| Any case, shipped copy | every run | 0 |

When it hangs, `ClosePseudoConsole` returns at once, but conhost and the shell keep running
and the output pipe never closes. A resize that reaches the Windows copy while it is still
starting makes it lose the close. The shipped copy does not have this bug.

Change: `resize_succeeds` runs on the shipped copy only.

Change 2 (after the final review): `Pty` now waits 2 s for the output pipe to end. If it
does not end, `Pty` ends the child and cancels the reader's blocked read. The test
`inbox_drop_after_early_resize_is_bounded` checks 20 early-resize closes per run. It passed
5 runs (100 closes) with no hang. The last run hit the bug 3 times and recovered each time,
and no conhost was left running. `Pty` can also move to another thread now.

Effect on milestone 1: the spec keeps the Windows copy as a fallback (with a banner). A
close on that copy can take about 2 s, so milestone 1 should close panes off the UI thread.
